# ШАГ 13: Kill Switch & Safe Mode

**Статус:** Обязательный механизм безопасности Tender Shield Pro

**Цель:** Обеспечить, чтобы при любом из следующих событий:
- деградация LLM
- подозрение на галлюцинации
- нарушение guardrails
- регуляторное требование
- security-инцидент
- on-prem / offline режим
- ручное решение руководства

➡️ **система НЕ ПЕРЕСТАВАЛА БЫТЬ ЧЕСТНОЙ**, а переходила в безопасный, детерминированный режим.

---

## 🧱 БАЗОВЫЙ ПРИНЦИП (НЕ НАРУШАТЬ)

**Лучше отсутствие reasoning, чем неконтролируемое reasoning.**

---

## 1️⃣ ЧТО ТАКОЕ KILL SWITCH В Tender Shield Pro

**Kill Switch — это НЕ выключение системы.**

Это:
- отключение LLM-reasoning слоя (ШАГ 4)
- сохранение Evidence, Audit, Versioning
- перевод системы в Safe Mode

---

## 2️⃣ ТРИ РЕЖИМА РАБОТЫ (КАНОНИЧЕСКИЕ)

### 🟢 NORMAL MODE

- reasoning включён
- все шаги 3–6 активны

### 🟡 SAFE MODE (Kill Switch ON)

- reasoning ОТКЛЮЧЁН
- Evidence доступен
- Decision = ограниченный
- явная маркировка

### 🔴 LOCKDOWN MODE

- reasoning отключён
- новые решения запрещены
- доступ только к Audit Trail

**❌ Других режимов быть не может.**

---

## 3️⃣ ТРИГГЕРЫ АКТИВАЦИИ KILL SWITCH

Kill Switch **ОБЯЗАН** активироваться при любом из:

### Автоматические:

- CI guardrail FAIL в production
- нарушение Red Team сценария
- расхождение snapshot'ов
- непредсказуемый вывод модели
- отказ MCP-валидации

### Ручные:

- команда безопасности
- compliance
- enterprise-клиент
- режим on-prem / offline

**Активация всегда логируется.**

---

## 4️⃣ SAFE MODE — ПОВЕДЕНИЕ СИСТЕМЫ

### В Safe Mode система НЕ ИМЕЕТ ПРАВА:

- ❌ интерпретировать риски
- ❌ формировать новые Decision Graph
- ❌ менять классификации

### Разрешено:

- ✅ показывать последнее актуальное решение
- ✅ показывать Evidence Objects
- ✅ показывать Audit Trail
- ✅ явно сообщать об ограничениях

### Обязательный UI-текст:

> **«Reasoning временно отключён.  
> Система работает в безопасном режиме.  
> Новые управленческие выводы не формируются.»**

---

## 5️⃣ LOCKDOWN MODE — КОГДА И ЗАЧЕМ

Lockdown Mode используется, если:

- целостность данных под вопросом
- есть риск юридического вреда
- требуется регуляторная пауза

В этом режиме:

- запрещены новые анализы
- запрещены новые выводы
- доступен только просмотр истории

---

## 6️⃣ АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ

Kill Switch **ОБЯЗАН**:

- ✅ быть реализован вне LLM
- ✅ быть детерминированным
- ✅ работать без модели
- ✅ быть тестируемым в CI
- ✅ быть видимым в UI и API

**❌ Запрещено:**

- «мягкое» отключение
- скрытая деградация
- fallback на "упрощённый reasoning"

---

## 7️⃣ CI ПРОВЕРКИ (ОБЯЗАТЕЛЬНО)

CI **ОБЯЗАН**:

- уметь эмулировать Kill Switch
- проверять Safe Mode вывод
- проверять отсутствие reasoning вызовов
- проверять UI-маркировку

Если Safe Mode:

- выдаёт решение
- интерпретирует риски
- меняет формулировки

➡️ **CI FAIL**

---

## 8️⃣ АУДИТ И ОТВЕТСТВЕННОСТЬ

Каждая активация Kill Switch:

- имеет ID
- имеет причину
- имеет timestamp
- связана с версиями системы

**Это юридически значимое событие.**

## 📦 РЕАЛИЗАЦИЯ

### Backend

- `backend/kill_switch_types.py` — типы и константы
- `backend/kill_switch_manager.py` — управление Kill Switch
- `backend/safe_mode_handler.py` — обработка Safe Mode
- `backend/main.py` — интеграция в анализ

### Frontend

- `frontend/src/components/KillSwitchBanner.tsx` — UI-компонент для отображения режима

### API Endpoints

- `GET /api/kill-switch/status` — получение статуса
- `POST /api/kill-switch/activate` — активация (только для администраторов)
- `POST /api/kill-switch/deactivate` — деактивация (только для администраторов)
