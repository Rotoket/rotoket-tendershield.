## Тендер.Щит — системный обзор

> **Этот документ — каноническое текстовое описание системы Тендер.Щит.**  
> Он фиксирует замысел, архитектуру и управленческий канон, а не технические детали реализации.

---

## 1. Назначение и роль системы

- **Имя системы**: `Тендер.Щит`  
- **Тип системы**: Decision Intelligence + Compliance Layer  
- **Основная ценность**: помочь директору/собственнику принять, зафиксировать и защитить управленческое решение об участии / неучастии / участии с условиями / переносе решения по тендеру.

### 1.1. Ключевые роли

- **Director (директор / собственник / уполномоченное лицо)**  
  - Принимает и фиксирует управленческое решение.  
  - Имеет право экспорта Board Pack и Compliance‑отчётов.  
  - Имеет доступ к полному Audit Trail.  
  - Не выполняет технический анализ, не настраивает систему.

- **Expert (тендерный специалист / аналитик)**  
  - Загружает и подготавливает тендерную документацию.  
  - Запускает анализ (single / пакет / глубокий аудит).  
  - Готовит управляемые риски и пояснения.  
  - **Не** фиксирует финальное решение и не экспортирует Board Pack.

### 1.2. Основные принципы

1. **Decision > Analysis** — система существует ради управленческого решения, а не ради аналитики.  
2. **Audit Trail как источник истины** — любые управленческие события фиксируются в неизменяемом журнале.  
3. **Evidence‑based выводы** — каждый вывод опирается на конкретные фрагменты документов.  
4. **Язык директора** — короткие, протокольные формулировки без рекомендаций и без «AI‑лексики».  
5. **Необратимость решения** — зафиксированное решение не редактируется, изменение = новое решение.

## 2. Высокоуровневая архитектура

Система состоит из трёх основных слоёв:

1. **Frontend (React + TypeScript + Vite + Tailwind)**  
   - UI для экспертов и директоров.  
   - Реализация канонического порядка экранов:  
     `Context → DealBreakersPanel → DecisionBlock → FinancialMetricsGrid → HeroVerdict → AIConsultantIntro → RiskNarrative → DecisionSupport → Details`.
   - Реализация UI‑гвардов (см. раздел 6).

2. **Backend (Python + FastAPI + Pydantic + SQLite/PostgreSQL)**  
   - Оркестрация анализа документов.  
   - Инкапсуляция LLM‑логики и промптов (Decision Preview, Advisory, MCP‑слой).  
   - Управление Audit Trail, экспорт Board Pack и Compliance‑отчётов.

3. **AI / MCP‑слой (Model Context Protocol + Ollama‑модели)**  
   - Qwen2.5‑coder, LLaMA, Mistral и др.  
   - Работают как **аналитические модули**, а не как самостоятельные субъекты.  
   - Обязаны возвращать данные в каноническом JSON‑формате (DecisionPreviewData и др.) и соблюдать языковой канон.

## 3. Основные бизнес‑объекты

### 3.1. Deal Snapshot (Контур сделки)

**Канон**: ни один управленческий вывод не может существовать без Deal Snapshot.

- Располагается **строго первым блоком** на экране `DecisionPreview`, перед любыми выводами.
- **5 обязательных полей**:
  1. **Заказчик / организатор закупки** — как в документации.
  2. **Предмет закупки** — формулировка из документа (первая строка `summary` или из паспорта ТЗ).
  3. **Цена контракта / НМЦК**:
     - `Определена: XX XXX XXX ₽`,  
     - или `Диапазон / НМЦК: до XX XXX XXX ₽`,  
     - или `Не зафиксирована в документах`.
  4. **Правовой режим закупки** — `44‑ФЗ / 223‑ФЗ / коммерческая закупка`, с указанием источника (Извещение/документация).
  5. **Документы, принятые в анализ** — перечень 3–5 ключевых файлов / агрегированная формулировка:  
     «В анализ включено N ключевых документа».

**Особые правила:**

- Если данных нет — система **не скрывает поле**, а выводит: «Не зафиксирован(а) в документации».  
- Без статуса `dealSnapshot.status === "complete"`:
  - **запрещено** рендерить Decision Preview,  
  - **запрещено** фиксировать решение,  
  - **запрещено** экспортировать Board Pack / Executive Brief / Compliance‑отчёты.

### 3.2. Decision Layer и UserDecision

**UserDecision** (канон):

- `participate` — УЧАСТВОВАТЬ  
- `participate_with_conditions` — УЧАСТВОВАТЬ С КОНТРОЛЕМ / С УСЛОВИЯМИ  
- `do_not_participate` — НЕ УЧАСТВОВАТЬ  
- `postpone` — ОТЛОЖИТЬ РЕШЕНИЕ

**Правила:**

- Решение создаётся и фиксируется **только** через `DecisionBlock` в режиме Director.  
- Решение имеет статус «существует», только когда зафиксировано (есть `decision_fixed` + `DECISION_CONFIRMED_BY_DIRECTOR` в Audit Trail).  
- Изменение решения после фиксации невозможно; новое решение = новая запись в истории с новым хэшем.

### 3.3. Audit Trail (управленческий журнал)

**AuditEvent** (минимальный набор полей):

- `eventType` — тип события (`analysis_started`, `analysis_completed`, `decision_fixed`, …).  
- `timestamp` — время в UTC (плюс локальное представление в UI).  
- `actor` — `{ role: 'director' | 'expert' | 'system', id: string }`.  
- `entityType` — `single` / `package` / `report`.  
- `entityId` — идентификатор анализа/тендера/отчёта.  
- `snapshot` — минимальный срез состояния (вердикт, score, decision, dealBreakersCount, ИУН, ключевые документы и т.п.).

**Канонические события:**

- Аналитические:
  - `analysis_started`  
  - `analysis_completed`  
  - `key_documents_selected`
- Управленческие:
  - `decision_draft_created`  
  - `decision_viewed`  
  - `decision_fixed`
- Рисковые:
  - `deal_breaker_detected`  
  - `management_load_high`
- Юридически значимые:
  - `decision_confirmed_by_director`  
  - `board_pack_exported`  
  - `compliance_exported`  
  - `analytical_view_requested` (просмотр пояснения директором)

**Правила Audit Trail:**

- **append‑only**, записи не удаляются и не редактируются.  
- Любая смена решения / повторный анализ создаёт новые события, не перезаписывая историю.  
- UI читает Audit Trail только для просмотра и экспорта; **не имеет права переписывать прошлое**.

### 3.4. Evidence Layer и управляемые риски

**RiskEvidence** (канон):

- `document_id` — идентификатор файла (опционально).  
- `document_name` — фактическое название документа («Проект договора», «Извещение», …).  
- `section_ref` — ссылка на раздел/пункт (`"п. 6.3"`, `"Раздел IV"`).  
- `quote` — дословная выдержка 1–3 строки.

**ManagedRisk / CONTROLLED_RISK:**

- `id`, `title` — название управляемого риска.  
- `impact` — управленческое последствие (`legal` / `financial` / `operational` описывается на языке последствий).  
- `control` — как риск может быть управляем до подачи/в ходе исполнения.  
- `evidence: RiskEvidence[]` — **обязателен**.

**Жёсткие правила:**

1. **Риск без Evidence = не существует.**
   - Не отображается в UI.  
   - Не учитывается в ИУН.  
   - Не попадает в Board Pack / отчёты.
2. В UI для директора:
   - по умолчанию показывается `название риска + документ + пункт`,  
   - при раскрытии — блок «Источник риска»: документ, пункт, цитата, суть расхождения, управленческий эффект, статус.
3. Типы `interpretation_type`:
   - `literal` — прямое условие,  
   - `conflict` — противоречие,  
   - `absence` — отсутствие обязательного параметра,  
   - `ambiguity` — двусмысленность.

### 3.5. Индекс управленческой нагрузки (ИУН)

**ИУН = A + B + C + D**, где компоненты отражают:

- A — документальные противоречия, конфликты условий.  
- B — финансовая неопределённость (НМЦК, аванс, штрафы, обеспечение).  
- C — юридико‑процедурная сложность.  
- D — объём ручного управленческого контроля до и после подачи заявки.

**Шкала интерпретации:**

- `0–30` — стандартное участие, делегируемо.  
- `31–50` — участие при управленческом контроле.  
- `51–70` — участие только при осознанном решении директора.  
- `71–85` — участие под вопросом, требует отдельного управленческого решения.  
- `86–100` — управленчески нецелесообразно.

**Связь с Evidence:**

- `conflict` → +15 к компоненту (A/C),  
- `absence` → +10 к компоненту (B),  
- `ambiguity` → +5 к компоненту (A/C/B в зависимости от контекста),  
- `literal` — фиксирует наличие, но не всегда добавляет нагрузку.

## 4. Канон принятия решения (матрица DEAL BREAKER × ИУН)

### 4.1. Ось X — DEAL BREAKER

- Если `DEAL BREAKER = true` → **РЕШЕНИЕ: НЕ УЧАСТВОВАТЬ** (без альтернатив).

### 4.2. Ось Y — Индекс управленческой нагрузки

При `DEAL BREAKER = false` решение определяется по ИУН:

- `0–30` → **УЧАСТВОВАТЬ** (делегируемо, стандартный контроль).  
- `31–50` → **УЧАСТВОВАТЬ С КОНТРОЛЕМ** (требуются управленческие подтверждения и фиксация допущений).  
- `51–70` → **УЧАСТВОВАТЬ ТОЛЬКО ПРИ ОСОЗНАННОМ РЕШЕНИИ** директора.  
- `71–85` → **УЧАСТИЕ ПОД ВОПРОСОМ** (требует отдельного решения о целесообразности).  
- `86–100` → **НЕ РЕКОМЕНДУЕТСЯ** (даже без DEAL BREAKER, управленчески нецелесообразно).

### 4.3. Поведение UI при высоком ИУН (≥ 51)

- Система обязана:
  - остановиться на этапе Decision Preview,  
  - явно объяснить, **почему** нагрузка высока (по компонентам A/B/C/D с цифрами),  
  - показать **что именно** придётся делать директору (список действий),  
  - указать **каковы последствия**, если это не сделать (отклонение, потеря обеспечения, репутационные эффекты и т.д. в форме «следствием является…»).
- Кнопки фиксации решения доступны, но сопровождаются формулировкой:
  - «Решение допустимо только при принятии управленческой нагрузки и фиксации ответственности».

## 5. Текстовый канон языка директора

### 5.1. Запрещённые формулировки

**Нельзя использовать:**

- «рекомендуем», «следует», «лучше», «стоит», «советуем»;  
- «вероятно», «возможно», «скорее всего», «может привести», «высокая вероятность»;  
- «AI считает», «модель предполагает», «на наш взгляд».

### 5.2. Канонические замены

- «Рекомендуем участвовать» → **«Основания для участия»**.  
- «Следует отказаться» → **«Формальные основания для отказа»**.  
- «Возможен риск» → **«Зафиксирован риск»**.  
- «Может привести к…» → **«Следствием является…»**.  
- «Вероятно отклонение» → **«Основания для отклонения»**.  
- «AI выявил» → **«В документации зафиксировано…»**.  
- «Система считает» → **«Анализ показал…»**.

### 5.3. Стиль

- Короткие, утвердительные предложения.  
- Без эмоций, эпитетов, усилителей («очень», «крайне», «значительно»).  
- При недостатке данных — явное указание:  
  - «В документации отсутствует указание…»,  
  - «Прямое подтверждение не зафиксировано»,  
  - «Данные недостаточны для управленческого вывода».

## 6. UI‑гварды и канон интерфейса

### 6.1. Порядок блоков на экране Decision Preview (НЕИЗМЕНЯЕМЫЙ)

1. **Deal Snapshot (Контур сделки)**  
2. **Управленческое решение (Decision Summary + матрица DEAL BREAKER × ИУН)**  
3. **Управляемые риски (только с Evidence)**  
4. **Индекс управленческой нагрузки (число + расшифровка)**  
5. **Audit & Responsibility (фиксация решения, статус, отсылки к Audit Trail)**  
6. (Опционально) **Аналитическое пояснение по запросу директора** — отдельный блок, не влияющий на решение.

### 6.2. Гварды

1. **Без полного Deal Snapshot**:
   - Decision Preview не рендерится;  
   - `DecisionBlock` не активен;  
   - Export (Board Pack, Exec Brief, Compliance) не доступен (кнопки не рендерятся).

2. **Риски без Evidence**:
   - не попадают в `dp.controlled_risks`;  
   - не учитываются в ИУН;  
   - рядом с блоком рисков может отображаться фраза:  
     **«Некоторые выявленные риски не имеют документального основания и исключены из управленческого вывода»**.

3. **После `decision_fixed = true`**:
   - экран переходит в режим **read‑only**;  
   - все элементы редактирования (кнопки фиксации, формы ввода) **не рендерятся**;  
   - доступен только просмотр, история, экспорт.

4. **Экспорт как финал цепочки**:
   - Экспорт Board Pack / Executive Brief / Compliance отчёта возможен только если:
     - Deal Snapshot `complete`,  
     - все управляемые риски имеют Evidence,  
     - ИУН рассчитан,  
     - решение зафиксировано (`decision_fixed` + `decision_confirmed_by_director`),  
     - в Audit Trail есть записи `analysis_completed` и `decision_fixed`.

5. **Попытка обхода канона**:
   - Любая операция, нарушающая канон (экспорт без решения, изменение зафиксированного решения, рендеринг частичного Decision Preview) должна быть заблокирована и зафиксирована в Audit Trail как событие ошибки/попытки.

## 7. Режимы «осознанного молчания» и «пояснение по запросу»

### 7.1. Режим A — Осознанное молчание

Система **не делает вывод** и не подменяет отсутствие данных догадками.

- Если данных недостаточно:
  - В UI показывается: **«Данные недостаточны для управленческого вывода»**.  
  - Никакие вероятностные формулировки не генерируются.
- Если аспект вне компетенции:
  - В UI: **«Оценка выходит за рамки компетенции системы»**.  
  - Примеры: стратегические решения холдинга, политические риски, нефинансовые репутационные эффекты.

### 7.2. Режим B — Аналитическое пояснение по запросу директора

**Director‑only артефакт**, не влияющий на решение.

- В модели `DecisionPreviewData` поле `director_explanation?: string`.  
- В UI:
  - по умолчанию **скрыто**,  
  - показывается блок:
    - заголовок: «Аналитическое пояснение (по запросу директора)»;  
    - дисклеймер: «Это пояснение не является управленческим решением и не подменяет ответственность директора»;  
    - кнопка: **«Показать аналитическое пояснение»**.
- При первом раскрытии:
  - создаётся событие `ANALYTICAL_VIEW_REQUESTED` в Audit Trail.  
  - пояснение отображается как текст (без рекомендаций и без AI‑лексики).
- Пояснение:
  - не участвует в расчёте ИУН;  
  - не включается в Board Pack / Executive Brief / Compliance‑отчёт;  
  - не влияет на решение;  
  - не показывается роли `Expert`.

## 8. Экспортные артефакты

### 8.1. Board Pack (канонический отчёт для совета директоров и аудита)

**Назначение**: зафиксировать управленческое решение по тендеру и его основания в формате, пригодном для совета директоров, внутреннего аудита и внешних проверок.

**Структура (3 страницы):**

1. **Страница 1 — Executive Summary**
   - Заголовок: «УПРАВЛЕНЧЕСКОЕ РЕШЕНИЕ ПО ТЕНДЕРУ» (номер, заказчик, режим, НМЦК, регион).  
   - Итоговое решение (РЕШЕНИЕ: УЧАСТВОВАТЬ / С КОНТРОЛЕМ / НЕ УЧАСТВОВАТЬ).  
   - Основания:  
     - Стоп‑факторы: выявлены / не выявлены.  
     - Количество управляемых рисков.  
     - Статус финансовой определённости.  
     - ИУН: `NN / 100` + краткая интерпретация.  
   - Ответственность: кто и когда принял решение, отметка о фиксации ответственности.

2. **Страница 2 — Управленческое обоснование**
   - Статус DEAL BREAKER + краткое объяснение (1–2 строки).  
   - Таблица управляемых рисков:
     - Риск,  
     - Основание (документ + пункт + краткая суть),  
     - Статус (управляемый / требует подтверждения).  
   - Расшифровка ИУН по компонентам A/B/C/D.

3. **Страница 3 — Audit & Trace**
   - Сводка Audit Trail:
     - Дата анализа,  
     - Дата фиксации решения,  
     - ID `trailId`,  
     - дата экспорта Board Pack.  
   - Юридический дисклеймер:
     - документ фиксирует управленческое решение;  
     - аналитические материалы носят вспомогательный характер;  
     - система **не принимает решения автоматически**.

**Условия экспорта:**

- Решение зафиксировано (`decision_fixed` + `decision_confirmed_by_director`).  
- Заполнен Audit Trail (есть минимум `analysis_completed` и `decision_fixed`).  
- Экран Decision Preview в read‑only режиме.  
- Все канонические гварды соблюдены (Deal Snapshot complete, Evidence‑полные риски, рассчитан ИУН).

### 8.2. Executive Brief (краткий управленческий отчёт, 1 страница)

**Назначение**: дать директору/заместителю краткую выжимку для принятия решения за 30 секунд (в PDF/печати/пересылке).

**Структура:**

1. Заголовок: «УПРАВЛЕНЧЕСКОЕ РЕШЕНИЕ ПО ТЕНДЕРУ».  
2. Контур сделки в одну строку:  
   - «Поставка ___ · НМЦК X млн ₽ · 44‑ФЗ / 223‑ФЗ / коммерческая закупка · (МСП/регион)».  
3. Итоговое решение (крупно):  
   - «УЧАСТВОВАТЬ / УЧАСТВОВАТЬ С УПРАВЛЕНЧЕСКИМ КОНТРОЛЕМ / НЕ УЧАСТВОВАТЬ».  
4. Основания (до 4 буллетов):
   - «Критических стоп‑факторов не выявлено / выявлены».  
   - «Выявлены управляемые риски (N)».  
   - «Финансовые параметры требуют подтверждения / достаточны».  
   - «Индекс управленческой нагрузки: NN / 100».  
5. Что требуется от директора (2–3 пункта):
   - «Подтвердить финансовую модель».  
   - «Принять управленческую нагрузку по контролю исполнения».  
6. Статус ответственности:
   - «Решение подлежит фиксации директором. Изменение после фиксации невозможно».

**Особенности:**

- Не содержит Evidence, цитат, юридических подробностей.  
- Не дублирует Board Pack, а служит его выжимкой.  
- Формируется **только на основе уже зафиксированного решения**.

---

## 9. Жизненный цикл анализа и решения

1. **Загрузка и отбор документов**
   - Expert загружает 3–5 ключевых документов («Ключевые документы» — режим по умолчанию).  
   - Система фиксирует `key_documents_selected` в Audit Trail.

2. **Запуск анализа**
   - Запуск single / package / deep audit.  
   - `analysis_started` → парсинг документов → `analysis_completed`.

3. **Формирование Decision Preview**
   - Backend формирует `AnalysisResult` и `DecisionPreviewData` (decision, ИУН, риски, evidence).  
   - Frontend строит:
     - Deal Snapshot,  
     - управленческое решение (матрица DEAL BREAKER × ИУН),  
     - управляемые риски (с Evidence),  
     - ИУН,  
     - блок Audit & Responsibility.  
   - При первом просмотре фиксируется `decision_viewed`.

4. **Формирование драфта решения**
   - Директор переходит к `DecisionBlock`, выбирает вариант решения, добавляет комментарий.  
   - Система может фиксировать `decision_draft_created`.

5. **Фиксация решения**
   - Директор подтверждает: «Я подтверждаю управленческое решение и принимаю ответственность» (чекбокс).  
   - Система проверяет роль (`Director`), повторно сверяет канон (Deal Snapshot, ИУН, Evidence).  
   - Создаёт `decision_fixed` + `decision_confirmed_by_director` в Audit Trail, с хэшем и snapshot’ом.  
   - Экран переходит в read‑only, появляется статус «Решение зафиксировано».

6. **Экспорт и аудит**
   - Доступен экспорт:
     - Board Pack,  
     - Executive Brief,  
     - Compliance‑отчёты.  
   - Фиксируются `board_pack_exported`, `compliance_exported` с ссылкой на `trailId` и `decisionRef`.

---

## 10. Роль и ограничения AI‑слоя

- AI‑модели:
  - не имеют права принимать решения;  
  - не формулируют рекомендации в лоб;  
  - обязаны возвращать структуру данных (DecisionPreviewData, RiskEvidence, ManagementLoadComponents) в соответствии с каноном;  
  - используют только канонические формулировки (без «AI считает»).

- MCP‑слой (контент/справка):
  - объясняет смысл показателей (ИУН, Deal Snapshot, RiskEvidence);  
  - не заменяет юридическое консультирование;  
  - оформляет ответы в языке директора: «в документации зафиксировано…», «анализ показал…».

## 11. Итог: что такое Тендер.Щит

**Тендер.Щит — это не «ещё один анализатор тендеров», а:**

- **Система управленческих решений**: переводит сырую тендерную документацию в управленческий протокол.  
- **Слой контроля и ответственности**: фиксирует, кто, когда и на основании чего принял решение.  
- **Инструмент доверия и аудита**: каждое решение можно защитить перед акционерами, регулятором и внутренним аудитом.  
- **Партнёр директора**, который:
  - не навязывает решений,  
  - не подменяет волю,  
  - говорит простым управленческим языком,  
  - всегда может показать, **на какие пункты документа опирается**.  

Это и есть конкурентное преимущество Тендер.Щит по сравнению с типичными «AI‑аудитами тендеров» и BI‑дашбордами.
