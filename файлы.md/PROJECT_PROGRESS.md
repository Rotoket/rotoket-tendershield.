# Tender Shield Pro — прогресс и план работ

## 1. Назначение проекта

Tender Shield Pro — сервис для умного анализа документации российских тендеров (44‑ФЗ/223‑ФЗ). Цель: дать опытному тендерному специалисту быстрый и структурированный ответ по пакету документов:

- Стоит ли участвовать (вердикт и красные флаги).
- Паспорт закупки (объект, НМЦК, сроки, регион, заказчик, закон).
- Финансовые условия (структура НМЦК, аванс, оплаты, обеспечения, риски потерь).
- Требования к участнику (лицензии, СРО, опыт, персонал, оборудование и т.д.).
- Спецификация объекта/товаров/услуг.
- Рекомендуемые действия (участвовать / не участвовать / запрос разъяснений / жалоба и т.п.).

## 2. Архитектура (кратко)

- **Backend**: FastAPI, специализированные анализаторы, RAG‑движок по законам, интеграция с Ollama (локальные LLM).
- **LLM**: Ollama‑модели, отдельный более тяжёлый профиль под "Базу знаний" (вопросы по законам и разъяснениям).
- **RAG**: индекс законов и правовых материалов, быстрый поиск + генерация ответов.
- **Frontend**: React + TypeScript, единый экран "Анализ тендера" c хаб‑дашбордом и интеграцией с калькулятором и генератором документов.

## 3. Использование папки tender/ как обучающего корпуса

Папка `tender` (8 подпапок) — это **обучающий корпус** для выделения универсальных фраз и реперных точек по разным отраслям:

1. `tender1 1 stroyka` — строительство / ремонт моста, смета, отчёт по осмотру, проект договора, требования к заявке.
2. `tender 2 nedvijkka` — недвижимость и обслуживание объектов.
3. `tender 3 injiniring` — инженерные / проектные услуги, несколько приложений.
4. `tender 4 postavra` — поставка товаров, калькуляции НМЦК, ТЗ.
5. `tender 5 mebel` — мебель.
6. `tender 6 it` — ИТ‑поставки и услуги.
7. `tender 7 oxrana` — охранные услуги.
8. `tender 8` — универсальный шаблон (Описание, Обоснование НМЦК, Требования к заявке, Проект договора).

На основе анализа этих папок создан файл `backend/tender_reper_points.md` с реперными точками по отраслям (construction, real estate, engineering, goods, IT, security). Он служит чек‑листом для разработки правил и LLM‑промптов.

## 4. Что уже сделано (по коду)

### 4.1. Общий анализ и хаб‑дашборд

- Реализован единый экран анализа тендера на фронтенде (пакет документов + интеграция с калькулятором и генератором документов).
- Все ключевые вердикты и уровни риска локализованы на русский язык ("Не участвовать", "Осторожно", "Можно участвовать").
- Хаб показывает:
  - Итог по пакету (средний балл, вердикт, краткое резюме).
  - Паспорт закупки.
  - Финансы и сроки.
  - Красные флаги.
  - Интеграцию с калькулятором и генератором документов.

### 4.2. Финансовый анализ и НМЦК

- В `FinancialAnalyzer.analyze_nmck` добавлены расширенные паттерны для извлечения НМЦК, включая типичные формулировки из строительных протоколов и смет:
  - "Начальная (максимальная) цена контракта составляет ... рублей ... копеек".
  - Фразы, где НМЦК упоминается вместе с локальным сметным расчётом.
- Добавлен fallback: если нет явного совпадения по шаблонам, из текста вытаскиваются все суммы с "руб/₽", выбирается **максимальная** как кандидат НМЦК.
- Вычисляется как строковое (`nmck`), так и числовое (`nmck_numeric`) значение.
- В `analyze_single_file` НМЦК из регулярок/финансового анализатора прокидывается в:
  - `result.passport.nmck`.
  - `result.financialSummary.nmck`.
- На основе НМЦК считается "финансовый удар" (штрафы, обеспечение, аванс, оборотные средства), и эти значения добавляются в `financialSummary`.

### 4.3. Реперные точки (backend/tender_reper_points.md)

- Сформирован подробный список реперных точек по всем 8 типам тендеров:
  - Общий паспорт закупки.
  - Финансовые условия (НМЦК, структура цены, аванс, оплаты, обеспечения).
  - Условия договора (штрафы, односторонний отказ, РНП, гарантийные обязательства).
  - Требования к участнику и состав заявки.
  - Специфика по отраслям: строительные отчёты и сметы, недвижимость, инженерные услуги, поставки товаров, ИТ, охрана.
- Этот документ используется как основа для разработки детекторов типов документов, схем JSON и промптов для LLM.

### 4.4. Новый docType и inspectionSummary (строительные отчёты)

В `backend/main.py` реализованы:

- `detect_document_type(text, filename)` — грубая классификация документа.
  - Сейчас определяет **INSPECTION_REPORT** по типичным фразам:
    - "ОТЧЕТ по осмотру ..." / "ОТЧЁТ по осмотру ...".
    - "Техническое заключение" + "состояние".
    - "акт" + "обследован" + "мост".
  - Все остальные документы помечаются как `GENERIC`.

- `extract_inspection_summary(text)` — вытаскивает базовые параметры из отчёта по осмотру моста:
  - `condition` — обобщённое состояние ("аварийное", "удовлетворительное" и т.п.).
  - `wearPercent` — общий износ конструкций в процентах (по фразам вида "общий износ ... 45 %").
  - `lengthMeters` — длина моста/объекта ("длина моста ... 52,5 м").
  - `recommendedWorkKind` — рекомендованный вид работ (ремонт / капремонт / реконструкция), если это явно указано.
  - `normativeRefs` — список коротких фрагментов с упоминанием СП, типовых конструкций, СНиП, ГОСТ.
  - `safetyMeasures` — меры безопасности до ремонта (запрет движения, знаки и т.п.), если удаётся надёжно извлечь.

Изменения в `analyze_single_file`:

- После извлечения цены через `extract_price_regex` теперь:
  - Определяется `docType = detect_document_type(text, filename)`.
  - Если тип документа `INSPECTION_REPORT`, вызывается `extract_inspection_summary(text)`.
- В итоговый JSON добавлены поля:
  - `docType` — строка.
  - `inspectionSummary` — объект с полями выше (или пустой dict для не‑техотчётов).

## 8. Стратегия ИИ, авторизации и облачного развёртывания

### 8.1. Базовая LLM‑модель и архитектура

- Основная модель анализа: локальная модель `qwen2.5-coder:7b` через Ollama.
  - Используется для всех режимов анализа документов (одиночный `/api/analyze` и пакетный `/api/analyze-package`).
  - Настройки:
    - низкая температура (0.1) и формат `json` в `get_analysis_llm()` для детерминированного структурированного вывода;
    - таймаут 5 минут.
- Вспомогательная модель (потенциал на будущее): более лёгкая модель (например, `qwen2.5-coder:1.5b`) для чата/подсказок и быстрых ответов.
  - Архитектурно поддерживается тем же `llm_client.py`, достаточно вынести имя модели в отдельный setting.
- RAG по законам и локальная база знаний остаются отдельным слоем (см. п. 6.5), LLM используется как мозг над ими.

### 8.2. Стратегия авторизации, триалов и тарифов

Текущая реализация (см. `auth.py`, `main.py`, `database.py`, `payment.py`) поддерживает следующую модель:

1. **Демо без регистрации**
   - Если запрос в `/api/analyze` без JWT‑токена, используется `DemoSession`:
     - каждому браузеру/устройству выдаётся `demo_session_id` (cookie или заголовок);
     - демо‑сессия хранит собственные лимиты (`max_analyses` и т.п.), проверка через `DemoSession.can_analyze()`.
   - При достижении лимита:
     - сервер возвращает 429 с заголовками `X-Demo-Limit: true`, `X-Suggest-Registration: true`;
     - фронтенд должен показать модалку «Зарегистрируйтесь, чтобы продолжить и получить 7‑дневный триал».

2. **Регистрация и 7‑дневный триал**
   - При регистрации создаётся пользователь с полями:
     - `plan_type = "trial"`;
     - `trial_end = now + 7 дней` (метод `is_trial_active()` уже реализован в модели `User`).
   - Пока `plan_type == "trial"` и `is_trial_active()` возвращает `True`:
     - `check_user_can_analyze()` разрешает анализ без жёстких лимитов (или с высоким лимитом по отдельному тарифу "Trial").
   - После истечения триала:
     - в `/api/analyze` при первом анализе с истёкшим триалом пользователь автоматически переводится на тариф `Free`:
       - `plan_type = "free"`;
       - `tariff_id` указывает на тариф Free с ограничением `analyses_limit` (например, 5–10 анализов/мес).

3. **Free и платные тарифы**
   - Для пользователей с `plan_type = "free"` или платным тарифом (`pro` и др.) используется таблица `Tariff` и модель `Usage`:
     - `Tariff.analyses_limit` задаёт месячный лимит анализов;
     - `Usage` хранит счётчики анализов/пакетов по (user_id, year, month).
   - Функция `check_user_can_analyze(user, db)` реализует единый контроль лимитов:
     - безлимит (`analyses_limit = -1`);
     - ограниченный лимит + человекочитаемое сообщение при превышении.

4. **Оплата и подписка**
   - Модуль `payment.py` (Yookassa) и таблица `Tariff` позволяют активировать подписку:
     - `process_payment_webhook()` / `activate_subscription_mock()`:
       - устанавливают `user.tariff_id`, `user.plan_type` (например, `pro`), `subscription_start`, `subscription_end` (+30 дней);
       - при наличии активного триала — обнуляют `trial_end`.

5. **Гибкость политики после триала**
   - Поведение после 7 дней триала можно настроить без больших изменений кода:
     - «мягкий» вариант — переводить на Free‑тариф с малым лимитом (уже реализовано);
     - «жёсткий» вариант — установить для Free‑тарифа нулевой лимит и в `check_user_can_analyze()` возвращать отказ до покупки тарифа.

Рекомендуемая модель на старте:

- Открытый демо‑режим без регистрации (ограниченное количество анализов).
- После исчерпания демо — предложение регистрации и включение полнофункционального 7‑дневного триала.
- После 7 дней — автоматический перевод на Free с небольшим лимитом и подсказкой оформить платный тариф.

### 8.3. План облачного развёртывания (черновой вариант, Timeweb Cloud)

Цель: развернуть Tender Shield Pro как SaaS в облаке (например, Timeweb Cloud), сохранив локальную модель Ollama + FastAPI + Postgres.

1. **Компоненты прод‑инфраструктуры**
   - Backend‑контейнер (FastAPI + Celery/фоны при необходимости).
   - Frontend‑контейнер (React/Vite, статический хостинг за Nginx).
   - Отдельный контейнер/ВМ с Ollama и моделью `qwen2.5-coder:7b`.
   - Управляемая PostgreSQL (или отдельный контейнер/ВМ под БД).
   - S3‑совместимое хранилище или volume для файлов документов (по возможности).

2. **Минимальные требования по железу для Ollama + 7B**
   - Для модели `qwen2.5-coder:7b` в режиме INT4/INT8 достаточно GPU с 16 ГБ VRAM (рекомендовано 16–24 ГБ для одновременной обработки нескольких запросов).
   - CPU и RAM на GPU‑ноде:
     - 4–8 vCPU;
     - 16–32 ГБ RAM.
   - Для небольшого числа одновременных пользователей (1–5) этого достаточно, далее можно масштабировать горизонтально (несколько GPU‑нод за балансировщиком).

3. **Рекомендации по Timeweb Cloud (ориентировочно)**
   - Использовать отдельную GPU‑машину для Ollama + LLM:
     - GPU: не менее 16 ГБ VRAM;
     - CPU: 4+ vCPU;
     - RAM: 16+ ГБ.
   - Отдельную CPU‑машину для API/БД:
     - FastAPI + Nginx/Traefik: 2–4 vCPU, 4–8 ГБ RAM;
     - PostgreSQL: 2–4 vCPU, 8–16 ГБ RAM и SSD‑хранилище (в зависимости от объёма истории и логов).
   - Обязательно настроить:
     - HTTPS (Let’s Encrypt/сертификат),
     - резервные копии БД,
     - мониторинг нагрузки на GPU/CPU, чтобы вовремя увеличивать ресурсы.

4. **Следующие шаги по развёртыванию**
   - Описать Docker‑компоуз/Helm‑chart для всех сервисов.
   - Подобрать конкретный тариф на Timeweb Cloud (GPU‑сервер с 16–24 ГБ VRAM, отдельный CPU‑сервер для API/БД) по актуальным ценам.
   - Настроить переменные окружения (`TENDER_...`) для прод‑окружения (URL БД, секреты, CORS, модель Ollama).
