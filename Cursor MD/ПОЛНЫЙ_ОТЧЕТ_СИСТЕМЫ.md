## Общий обзор системы Tender Shield Pro

Tender Shield Pro — это SaaS‑сервис для **интеллектуального анализа тендерной документации РФ** (44‑ФЗ / 223‑ФЗ и смежные нормы) с поддержкой:
- автоматического анализа документов,
- выявления рисков и «красных флагов»,
- рекомендаций по участию,
- экспорта в PDF/Excel,
- демо‑режима без регистрации,
- платёжной системы (YooKassa),
- аналитики по пользователям и системе,
- генерации юридических документов (v2: «Обоснованное несогласие»).

Текущий статус: **боевой backend + продвинутый frontend, все backend‑тесты зелёные, PostgreSQL настроен, LLM‑failover реализован.**

---

## Архитектура и стек

### Backend (`/backend`)

- **FastAPI** — HTTP API, авторизация, бизнес‑логика.
- **PostgreSQL 16** — основная БД, SQLAlchemy ORM.
- **SQLAlchemy + Alembic** — модели, миграции.
- **Ollama + langchain‑ollama** — LLM для анализа и генерации текстов.
- **Redis (опционально)** — кеширование (подключение через `cache_service.py`).
- **ReportLab, openpyxl** — экспорт в PDF и Excel.
- **YooKassa SDK** — приём платежей.
- **PyMuPDF, Docx2txt** — чтение PDF/DOC/DOCX.
- **pytest (+pytest-asyncio, anyio)** — тесты.

Ключевые файлы backend:
- `main.py` — основной файл API, эндпоинты, бизнес‑логика.
- `database.py` — модели БД, создание движка, `SessionLocal`, `init_db`, `create_default_tariffs`.
- `config.py` — настройки через `pydantic_settings` (`TENDER_*` env).
- `llm_client.py` — базовые функции работы с Ollama (анализ/чат).
- `auth.py` — JWT‑авторизация, регистрация/логин, фикстуры тестового пользователя.
- `legal_data.py` — встроенная правовая база (сниппеты).
- `cache_service.py` — кеширование результатов анализа (по хэшу документа).
- `analytics.py`, `analytics_export.py` — аналитика и её экспорт.
- `payment.py` — логика платежей и подписок (YooKassa).
- `pdf_export.py`, `excel_export.py` — экспорт отчётов.
- `rate_limiter.py` — лимитирование запросов (SlowAPI).
- `notifications.py` — уведомления пользователям.
- `registry_checker.py`, `specialized_analyzers.py`, `rag_engine.py` — дополнительные проверки и продвинутый анализ.
- `check_db_connection.py` — диагностика PostgreSQL.
- Множество `.md`‑файлов с рабочими логами и отчётами.

### Frontend (`/frontend`)

- **React + TypeScript + Vite + Tailwind CSS.**
- Основные разделы (по `frontend/README.md` и коду `src/`):
  - Анализ одного документа,
  - Пакетный анализ,
  - История,
  - Профиль / Тарифы / Подписка,
  - Экспорт отчётов,
  - Чат с AI,
  - База знаний.

Фронт уже интегрирован с ключевыми эндпоинтами backend (`/api/analyze`, `/api/profile`, `/api/history`, `/api/chat`, `/api/export/*`, `/api/analytics/*`).

## Модели данных (главное)

`database.py`:

- `User` — пользователи, триалы, подписки, тарифы.
- `Tariff` — тарифные планы (Free, Start, Pro, Enterprise).
- `DemoSession` — демо‑сессии (анонимные пользователи, лимит 3 анализа/24ч).
- `Analysis` — результаты анализа одного документа.
- `PackageAnalysis` — результирующий анализ пакета документов.
- `Usage` — использование квот (сколько анализов сделал пользователь в месяц).
- `GeneratedDocument` — **НОВОЕ**: сгенерированные документы (обоснования, письма и т.п.).

И множество вспомогательных таблиц (для платежей, аналитики, уведомлений и т.д., см. `database.py`).  

БД по умолчанию: PostgreSQL (`tender_shield`), но есть fallback на SQLite при проблемах подключения (для dev/тестов).

## Ключевые эндпоинты backend

### 1. Здоровье и базовые сервисы

- `GET /api/health` — здоровье API (статус, CORS, timestamp).

### 2. Авторизация и профиль

- `POST /api/auth/register` — регистрация с автозапуском триала (14 дней).
- `POST /api/auth/login` — логин, выдача JWT токена.
- `GET /api/auth/me` — данные текущего пользователя.
- `GET /api/profile` — расширенный профиль: тариф, лимиты, использование, триал.
- `GET /api/tariffs` — список активных тарифов.

В `auth.py` предусмотрен **тестовый пользователь** для разработки: при отсутствии токена `get_optional_user` создаёт/возвращает `test@tendershield.pro`. Это облегчает локальную разработку, но в проде эту логику стоит отключить/ограничить.

### 3. Платежи и подписки

- `POST /api/payment/create` — создание платежа (YooKassa).
- `POST /api/payment/webhook` — обработка вебхуков от YooKassa.
- `GET /api/payment/mock-confirm` — мок‑подтверждение платежа (для тестов).

Работают поверх `payment.py`, который создаёт/активирует подписки, меняет тарифы и план‑типы пользователей.

### 4. Анализ документов

#### 4.1. Одиночный анализ

- `POST /api/analyze`  
  Параметры:
  - `file: UploadFile`,
  - `industry: Form("UNIVERSAL" | "IT" | "CONSTRUCTION" | "MEDICINE" | ...)`,
  - пользователь — авторизованный или демо.

Основной pipeline:
1. **Проверка тарифов и лимитов** (для авторизованных) и **лимита демо‑сессии** (3 анализа/24ч).
2. Валидация файла (`utils/file_validator.py`).
3. Временное сохранение файла на диск (`tempfile.mkstemp`, безопасное удаление через `safe_remove_file`).
4. Чтение документа (`PyMuPDFLoader`, `Docx2txtLoader` или текстовый режим).
5. Подготовка отраслевого промпта и **мега‑промпта** (паспорт, риски, спецификация и т.д.).
6. Вызов LLM через **failover‑функцию** `_safe_ollama_invoke`.
7. Парсинг JSON ответа (с fallback, если JSON кривой или LLM недоступен).
8. Дополнительные эвристики (IT/CONSTRUCTION/MEDICINE), специализированные анализаторы, реестры.
9. Сохранение результата в БД (`Analysis`), историю, кеш (`cache_service`).
10. Возврат структурированного JSON с полями:
    - `score`, `verdict`, `summary`, `passport`, `issues`, `specs`, `redFlags`, `financialSummary`, `timelineSummary`, `actions`.

Важно: если Ollama/LLM полностью недоступен, система **не падает** — работает fallback‑анализ на основе regex и жёстко прописанных эвристик, с пониженным score и предупреждением.

#### 4.2. Пакетный анализ

- `POST /api/analyze-package`  
  Принимает список файлов, прогоняет через `analyze_single_file` и собирает:
  - список `DocumentAnalysis`,
  - `summaryScore` (средняя оценка),
  - `verdict` по худшему документу,
  - `globalIssues` (собранные междокументные риски: НМЦК, режим закона, обеспечение, критичные риски).

### 5. История

- `GET /api/history` — история анализов текущего пользователя (из БД) + in‑memory история для анонимов (для обратной совместимости).

### 6. Правовая база и аналитика

- `GET /api/legal/search` — поиск по заготовленной базе правовых сниппетов (`LEGAL_SNIPPETS`).
- `GET /api/analytics/user/{user_id}` — аналитика по пользователю.
- `GET /api/analytics/system` — системная аналитика (для админа).
- `GET /api/analytics/timeline` — временная линия анализов.
- `GET /api/analytics/popular-industries` — популярные отрасли.
- `GET /api/analytics/average-scores` — средние оценки по отраслям.
- Экспорт аналитики: `GET /api/analytics/export/csv`, `GET /api/analytics/export/excel`.

### 7. Экспорт отчётов

- `GET /api/export/pdf/{analysis_id}` — экспорт анализа в PDF (авторизованные + ограничения для демо).
- `POST /api/export/pdf` — экспорт PDF по «сырым» данным (для неавторизованных).
- `GET /api/export/excel/{analysis_id}` — экспорт анализа в Excel.
- `POST /api/export/excel` — экспорт Excel по переданным данным.

Все экспорты проверяют права, демо‑ограничения и используют `pdf_export.py` / `excel_export.py`.

### 8. Демо‑режим

- Демо‑сессии отслеживаются через `DemoSession` + cookie/заголовок `X-Demo-Session-Id`.
- Лимит: 3 анализа за 24 часа, далее — HTTP 429 + заголовки `X-Demo-Limit: true`, `X-Suggest-Registration: true`.
- Отдельный эндпоинт: `GET /api/demo/session/{session_id}` — состояние демо‑сессии.

### 9. Чат

- `POST /api/chat` — простой чат с LLM, использует `_safe_ollama_invoke` в текстовом режиме (без JSON).

### 10. **Новая фича**: генерация документов v2

- `POST /api/documents/objection/{analysis_id}` — генерация документа **«Обоснованное несогласие»**.
  - Берёт `Analysis.result_json`,
  - Строит промпт для LLM с перечислением `issues`, `redFlags`, паспортных данных,
  - Через `_safe_ollama_invoke(..., format_json=False)` создаёт текст письма,
  - В случае падения LLM создаёт fallback‑письмо на основе имеющихся рисков,
  - Сохраняет результат в `GeneratedDocument` с `doc_type="OBJECTION_LETTER"`,
  - Возвращает объект `GeneratedDocumentResponse`.

Покрыто тестом `tests/test_generated_documents.py`.

## Failover‑система работы с LLM (Ollama)

В `main.py`:

- Конфигурация моделей:
  ```python
  OLLAMA_MODELS = [
      "qwen2.5:0.5b",  # основная (быстрая)
      "llama3:8b",     # резерв 1 (умная)
      "mistral:7b",    # резерв 2 (надёжная)
  ]
  ```

- Функция:
  ```python
  def _safe_ollama_invoke(prompt: str, format_json: bool = True) -> str:
      ...
  ```
  - для каждой модели создаёт `ChatOllama` с `temperature=0.1`, `timeout=300`, при `format_json=True` — `format="json"`;
  - пытается выполнить `invoke` и возвращает `.content`, если ответ достаточно длинный;
  - при ошибках логирует `logger.warning` и переходит к следующей модели;
  - если все модели упали — выдаёт `HTTPException(503, "Все AI-сервисы недоступны...")`.

Используется в:
- `analyze_single_file` (анализ документов);
- `chat_endpoint` (чат);
- `generate_objection_letter` (документо‑генерация).

Это делает систему **отказоустойчивой к падениям отдельных LLM‑моделей/конфигураций**.

## Чего не хватает для полноценного выхода «в боевой интернет»

### 1. Инфраструктура и деплой

**Нужно:**
- Выбрать и подготовить прод‑окружение:
  - VPS/облако (Hetzner, Selectel, Yandex.Cloud, etc.) или Kubernetes.
  - Операционная система (Ubuntu 22.04 LTS и т.п.).
- Настроить:
  - **Production PostgreSQL** (отдельный инстанс, резервное копирование, мониторинг).
  - **Ollama сервер** (GPU/CPU, установка нужных моделей, ограничение доступа извне).
  - **Reverse proxy (Nginx/Caddy)** с HTTPS (Let’s Encrypt), балансировкой и сжатием.
  - **Запуск backend как systemd‑сервис или через Docker/Compose.**
  - **Запуск frontend как статический билд** (`npm run build`, отдача через Nginx).

**Рекомендуемое направление:** 
- собрать `docker-compose.yml` с сервисами:
  - `backend` (FastAPI + Uvicorn/Gunicorn),
  - `frontend` (build + nginx),
  - `db` (PostgreSQL),
  - `ollama` (опционально, если удобно в контейнере),
  - `redis` (для кеша/лимитирования).

### 2. Безопасность и конфигурация

- Убрать/ограничить тестовую логику `get_optional_user` (тестовый пользователь без токена).
- Перевести все чувствительные настройки в переменные окружения/секреты, в т.ч.:
  - ключи JWT,
  - пароли PostgreSQL/Redis,
  - ключи YooKassa,
  - SMTP‑пароли.
- Ограничить доступ к Swagger (`/docs`) в проде (по IP или по флагу).
- Настроить CORS только на нужные прод‑домены.

### 3. Логирование и мониторинг

- Централизованное логирование (структурированные логи в файл или в стэк ELK/EFK).
- Метрики:
  - количество анализов,
  - среднее время ответа,
  - ошибки LLM/Оllama,
  - показатели по демо/платным пользователям.
- Аллерты (например, через Prometheus + Alertmanager или внешний сервис).

### 4. Масштабирование и лимиты

- Проверить и настроить более жёсткие лимиты по:
  - размеру файлов (сейчас 50 МБ),
  - количеству запросов (rate limiting),
  - числу одновременно обрабатываемых анализов.
- Отдельный воркер/очередь (Celery/RQ) для тяжёлых задач (анализ больших документов, сложные интеграции), чтобы не блокировать HTTP‑воркеры.

### 5. Интеграции (планы)

**Уже продумано (но не реализовано полностью):**
- Загрузка тендеров из `zakupki.gov.ru` (RSS/API) в виде `TenderFeedItem` и подписок по фильтрам.
- Интеграция с Bitrix24:
  - создание/обновление сделок по результатам анализов,
  - прикрепление PDF/Excel отчётов,
  - хранение `bitrix_deal_id` в `Analysis`.
- Интеграция с 1С (REST‑обмен, JSON через HTTP).

Эти интеграции не критичны для первого выхода в прод, но сильно усилят ценность продукта.

### 6. UX‑детали и фронтенд

- Добавить во frontend:
  - интерфейс для запуска генерации «Обоснованного несогласия» по уже проведённому анализу,
  - просмотр и скачивание сгенерированных документов,
  - явные подсказки по лимитам триала/тарифов/демо,

## Основные сложности и риски

1. **Зависимость от LLM и Ollama:**
   - Нагрузка на железо (GPU/CPU), время отклика, доступность моделей.
   - Требуется мониторинг и правильный выбор моделей для прод‑среды.

2. **Качество и предсказуемость LLM‑ответов:**
   - Несмотря на жёсткий JSON‑формат и мега‑промпт, LLM иногда может возвращать некорректный JSON→ защита реализована, но юридические тексты всё равно нужно проверять человеком.

3. **Юридическая ответственность:**
   - Система не может гарантировать юридическую безошибочность → нужно явно коммуницировать это в интерфейсе и документации.

4. **Нагрузка при росте пользователей:**
   - Одновременные большие анализы могут грузить LLM и БД→ нужны очереди, кеш, оптимизация и, возможно, шардирование анализа по воркерам.

5. **Платежи и соответствие законодательству:**
   - YooKassa требует корректной настройки webhook’ов, HTTPS, безопасности.

3. Настроить мониторинг и логирование.
4. Доделать ключевые UX‑экраны во frontend для новой функц
