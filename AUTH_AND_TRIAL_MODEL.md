# Модель авторизации, демо и тарифов Tender Shield Pro

Этот документ фиксирует, как должна работать авторизация, демо-режим, триалы и тарифы в Tender Shield Pro.
Он предназначен для backend- и frontend-разработчиков (в т.ч. в Cursor), чтобы поведение было единым.

## 1. Роли и состояния пользователя

Пользователь может находиться в одном из состояний:

1. **Гость (Demo)** — без регистрации и без JWT-токена.
2. **Зарегистрированный пользователь на триале (Trial)** — `plan_type = "trial"` + `trial_end` в будущем.
3. **Free-пользователь** — `plan_type = "free"`, привязан к тарифу Free.
4. **Платный пользователь (Pro/другие тарифы)** — `plan_type = "pro"` / `enterprise` и т.п., привязан к соответствующему тарифу.

Эти состояния задаются полями модели `User` (см. `database.py`):

- `plan_type: str` — `"trial" | "free" | "pro" | ...`.
- `tariff_id: int | None` — ссылка на запись в таблице `Tariff`.
- `trial_end: datetime | None` — дата окончания триала.
- `subscription_start`, `subscription_end` — период активной подписки.

## 2. Демо без регистрации

**Цель:** дать новичку попробовать систему без барьера регистрации.

### 2.1. Механика

- Если запрос в `/api/analyze` приходит без JWT-токена:
  - Backend создает / использует `DemoSession` (см. `DemoSession` в `database.py`):
    - идентификатор сессии берётся из `cookie` (`demo_session_id`) или заголовка `X-Demo-Session-Id`;
    - если сессия не найдена — создаётся новая (UUID).
  - Для каждой демо-сессии есть поля:
    - `analyses_count` — сколько анализов уже сделано;
    - `max_analyses` — лимит демо-анализов (задаётся в коде или миграцией, например 3–5);
    - методы `can_analyze()` и `increment_analyses()`.

### 2.2. Лимиты и поведение при их достижении

- Перед анализом:
  - Backend вызывает `demo_session.can_analyze()`.
  - Если лимит исчерпан:
    - возвращается `HTTP 429` с:
      - `detail` — текст для пользователя;
      - заголовки:
        - `X-Demo-Limit: true`;
        - `X-Suggest-Registration: true`.
- Frontend при получении такого ответа должен:
  - показать модальное окно с предложением регистрации;
  - объяснить, что регистрация даёт полноценный 7‑дневный триал.

## 3. Регистрация и триал

**Цель:** дать пользователю полноценный доступ на ограниченное время (7 дней) после регистрации.

### 3.1. Создание пользователя

При успешной регистрации (через отдельный `/api/auth/register`):

- Создаётся `User` со значениями:
  - `plan_type = "trial"`;
  - `trial_end = now + 7 дней`;
  - `tariff_id = NULL` или ID спец-тарифа "Trial" (по выбору).
- Пользователю возвращается JWT-токен (`/api/auth/login` или сразу при регистрации).

### 3.2. Проверка доступа к анализу

Во всех эндпоинтах анализа (`/api/analyze`, `/api/analyze-package`):

- Если пользователь авторизован (`current_user` не `None`):
  1. Если `plan_type == "trial"` и `user.is_trial_active()` → анализ разрешён без жесткого лимита.
  2. Если `plan_type == "trial"` и триал истёк (`is_trial_active() == False`):
     - Пользователь автоматически переводится на Free-тариф:
       - `plan_type = "free"`;
       - `tariff_id` = ID тарифа "Free";
       - изменения фиксируются в БД.
  3. После этого вызывается `check_user_can_analyze(user, db)`, который:
     - находит тариф по `tariff_id` или имени `Free`;
     - проверяет `Tariff.analyses_limit` и запись `Usage` за текущий месяц;
     - возвращает `(can_analyze: bool, message: str)`.
  4. Если `can_analyze == False`, `/api/analyze` возвращает `HTTP 429` с понятным текстом (лимит по тарифу).

### 3.3. Настройка длительности триала

- Длительность триала (7 дней) задаётся логикой расчёта `trial_end` при регистрации.
- Функция `User.is_trial_active()` должна сравнивать `trial_end` с текущим временем (`datetime.utcnow()`).

## 4. Free и платные тарифы

### 4.1. Таблица Tariff

В `Tariff` (см. `database.py`) задаются тарифы:

- Примеры:
  - `Free`: `analyses_limit = 5` (или 10) анализов в месяц.
  - `Pro`: `analyses_limit = -1` (безлимит) или высокий лимит (например, 200/мес).
  - `Enterprise`: индивидуальные настройки.

Главные поля:

- `name: str` — имя тарифа (`"Free"`, `"Pro"` и т.п.).
- `analyses_limit: int` — месяцный лимит:
  - `-1` = безлимит;
  - `>= 0` — конкретное количество анализов.

### 4.2. Таблица Usage

- `Usage` хранит счётчики по (user_id, year, month):
  - `analyses_count` — сколько анализов выполнено;
  - `packages_count` — сколько пакетных анализов выполнено (на будущее);
  - `tokens_used` — поле на будущее для токенов/объёма запросов.

### 4.3. Функция check_user_can_analyze

Логика (см. `main.py`):

1. Если `user.plan_type == "trial"` и триал активен → разрешаем.
2. Иначе находим тариф по `tariff_id` или по имени "Free" (если `plan_type == "free"`).
3. Если тариф не найден → отказ с сообщением «Тариф не найден».
4. Если `analyses_limit == -1` → безлимит, разрешаем.
5. Иначе:
   - читаем `Usage` за текущий год/месяц;
   - если `analyses_count >= analyses_limit`:
     - если ещё есть триал — возвращаем текст про лимит триала;
     - иначе — текст «Достигнут лимит анализов по тарифу (N/мес)».

## 5. Платная подписка (Yookassa / Mock)

### 5.1. Реальный платеж (Yookassa)

- Создание платежа:
  - Фронтенд вызывает `/api/payment/create` (или аналогичный эндпоинт), указывая выбранный тариф.
  - Backend создаёт платёж через Yookassa с `metadata` (`user_id`, `tariff_id`).
- Обработка webhook:
  - Yookassa вызывает `/api/payment/webhook`.
  - `payment.py/process_payment_webhook`:
    - проверяет `event == "payment.succeeded"`;
    - читает `user_id` и `tariff_id` из `metadata`;
    - находит пользователя и тариф;
    - устанавливает:
      - `user.tariff_id = tariff_id`;
      - `user.plan_type = tariff.name.lower()` (например, `"pro"`);
      - `subscription_start = now`;
      - `subscription_end = now + 30 дней`;
      - если был активный триал — завершает его (`trial_end = now`).

### 5.2. Mock-режим (без реальных платежей)

- Функция `activate_subscription_mock(user_id, tariff_id, db)` делает то же самое, но без обращения к Yookassa.
- Можно использовать в тестах / на dev‑стенде.

## 6. Политика после триала (варианты)

### 6.1. Мягкий вариант (рекомендуемый на старте)

- После 7 дней триала пользователь автоматически переводится на тариф `Free`:
  - `plan_type = "free"`;
  - `tariff_id` = Free;
  - `analyses_limit` для Free, например, 5 анализов/мес.
- Пользователь:
  - может продолжать пользоваться сервисом с ограничениями;
  - видит подсказку «Для безлимитного доступа оформите Pro» при достижении лимита.

### 6.2. Жёсткий вариант

- Free-тариф настраивается с `analyses_limit = 0`.
- После 7 дней триала анализ полностью недоступен, пока не будет активирован платный тариф.
- Логика `check_user_can_analyze` остаётся прежней, меняется только конфигурация тарифа.

## 7. Поведение фронтенда (кратко)

1. **Демо**:
   - Пока нет JWT:
     - отправляем запросы `/api/analyze` без токена;
     - при `429 + X-Demo-Limit: true` — показываем окно регистрации.

2. **После регистрации**:
   - Сохраняем JWT (localStorage/cookie);
   - все запросы к `/api/...` отправляем с `Authorization: Bearer <token>`.

3. **Истечение триала / лимит тарифа**:
   - При `429` без `X-Demo-Limit`:
     - показываем экран с сообщением об окончании триала или лимита тарифа;
     - предлагаем выбрать платный тариф и перейти к оплате.

4. **Отображение статуса**:
   - В профиле/шапке показываем:
     - текущий план (`Demo/Trial/Free/Pro`);
     - если есть триал — дату окончания и количество оставшихся дней;
     - если Free/Pro — сколько анализов использовано в этом месяце (значения из `/api/profile` или отдельного эндпоинта).
