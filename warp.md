# tender-shield-pro / warp.md

Этот файл фиксирует общую концепцию проекта **tender-shield-pro**, архитектуру, ключевые правила, реализованные инструменты и ближайшее направление развития. Его нужно **обновлять каждый день после создания важных функций/модулей**.

---

## 1. Миссия продукта

SaaS-сервис для **интеллектуального анализа тендерной документации РФ** (44-ФЗ / 223-ФЗ и смежные нормы), который позволяет тендерному специалисту за **2–3 минуты** получить уровень понимания, на который раньше уходили **2–3 часа** чтения ТЗ, извещения и проекта договора.

Ключевой пользователь: **тендерный специалист / руководитель отдела продаж**, работающий с госзакупками.


## 2. Базовые правила и ограничения

### 2.1. Язык интерфейса

- Правило №1: **весь пользовательский интерфейс только на русском языке**.
- Английский может использоваться только во внутренних комментариях/переменных в коде.

### 2.2. Юридические ограничения

- Система **не заменяет юриста** и не даёт «готовых схем» обхода закона.
- Везде, где система даёт выводы / рекомендации, есть **дисклеймер**, что это аналитическая оценка, а окончательное решение принимает специалист.
- Все юридические выводы по возможности сопровождаются:
  - ссылкой на норму закона (44-ФЗ, 223-ФЗ, 135-ФЗ, 152-ФЗ и др.);
  - рекомендацией сверяться с первоисточником и/или базой знаний.

### 2.3. Персональные данные (152-ФЗ)

- При загрузке документов всегда есть текст о том, что пользователь подтверждает законность использования и соглашается на обработку возможных ПДн.
- На экране авторизации реализованы чекбоксы:
  - пользовательское соглашение;
  - согласие на обработку ПДн по 152-ФЗ.
- Полноценные технические меры (шифрование, роли, маскирование ПДн, резервное копирование) планируются на backend/инфраструктурном уровне.

### 2.4. Rule 5 — Логирование и тесты

- Для **каждой важной новой функции**:
  - должна быть **логика логирования** (через единый UI-логгер);
  - по возможности должны быть **юнит-тесты** или хотя бы тесты утилитарных функций;
  - после завершения задачи должны запускаться **тесты (npm test)**.
- Важные пользовательские действия (кнопки, запуск анализа, скачивание отчётов, генерация документов) должны логироваться в человеко‑читаемом виде.


## 3. Архитектура

### 3.1. Backend (FastAPI)

- Фреймворк: **FastAPI**.
- Основные модули:
  - `backend/main.py` — точки входа API, логика анализа и истории.
  - `llm_client.py` (не описан здесь, но используется) — обёртка над LLM (Ollama/другой движок).
  - `legal_data.py` — статические правовые сниппеты для `/api/legal/search`.

#### 3.1.1. Основные модели

- `DocumentAnalysis` (Pydantic) — результат анализа одного документа на backend:
  - `filename`, `score`, `summary`, `verdict`, `passport`, `issues`, `specs`.
- `PackageAnalysisResponse` — ответ для пакетного анализа:
  - `packageId`, `summaryScore`, `verdict`, `documents: List[DocumentAnalysis]`, `globalIssues`.
- История:
  - `HistoryItem`, `HistoryResponse` — in-memory история анализов.
- Правовые сниппеты:
  - `LegalSnippet`, `LegalSearchResponse`.

#### 3.1.2. Основные эндпойнты

1. `POST /api/analyze`
   - Анализ **одного документа**.
   - Принимает: `file` (UploadFile), `industry` (UNIVERSAL / IT / CONSTRUCTION / MEDICINE).
   - Логика:
     - Сохранение файла во временный путь.
     - Вызов `analyze_single_file(...)`.
     - Запись результата в `HISTORY` как `kind="single"`.
     - Возврат JSON-объекта с полями: `score`, `summary`, `verdict`, `passport`, `issues`, `specs`, `redFlags`, `financialSummary`, `timelineSummary`, `actions`.

2. `POST /api/analyze-package`
   - Анализ **пакета документов** (мульти‑upload).
   - Для каждого файла вызывает `analyze_single_file`, собирает `DocumentAnalysis`.
   - Считает `summaryScore` (средний балл по документам).
   - Определяет `verdict` по худшему документу.
   - Строит `globalIssues` через `build_global_issues()` (несоответствие НМЦК, ФЗ, условий обеспечения, наличие критичных рисков).
   - Записывает событие в HISTORY как `kind="package"`.

3. `GET /api/history`
   - Возвращает последние анализы (`HistoryResponse`).

4. `GET /api/legal/search`
   - Простой поиск по заранее подготовленной базе правовых сниппетов (LEGAL_SNIPPETS).

5. `POST /api/chat`
   - Прокси к чат‑LLM (`get_chat_llm`).

#### 3.1.3. Внутренняя логика анализа

- `analyze_single_file(temp_path, filename, industry)`:
  - Чтение PDF/DOCX/TXT.
  - Формирование **мега‑промпта** для LLM:
    - паспорт тендера (НМЦК, регион, ФЗ, дедлайны, обеспечение);
    - `issues` — список рисков с цитатами и ссылками на закон;
    - `specs` — позиции спецификации (до ~15 позиций);
    - `redFlags` — красные флаги (brand only, демпинг, смешение лотов и др.);
    - `financialSummary` — НМЦК, ориентировочная себестоимость, комментарий по марже;
    - `timelineSummary` — дедлайны и оценка реалистичности сроков;
    - `actions` — рекомендованные шаги.
  - Защищённый разбор JSON с fallback.
  - Подстраховка НМЦК через regex (`extract_price_regex`).
  - Подсчёт `score` и вывод `verdict` (STOP / CAUTION / PARTICIPATE).
  - Отраслевые эвристики:
    - IT: бренды без "или эквивалент", смешение ПО и железа, иностранное ПО у госзаказчика и др.
    - CONSTRUCTION: жёсткие штрафы, скрытые работы без актов, ГОСТ без эквивалентов.
    - MEDICINE: срок годности, температурный режим, РУ и др.


### 3.2. Frontend (React + TypeScript + Vite)

- Стек: **React + TS + Vite**, дизайн — тёмная тема, акцентные цвета `#00d4ff`, `emerald`, `red`, `amber`.
- Навигация по приложениям через `AppView` (ANALYZER, AUDIT, GENERATOR, KNOWLEDGE, HISTORY, CALCULATOR, PROFILE, LOGIN).

#### 3.2.1. Ключевые типы (frontend/src/types.ts)

- `AnalysisResult` — результат одиночного анализа, расширенный:
  - `score`, `summary`, `verdict`, `passport: TenderPassport`, `deepAudit`, `issues`, `specs`, `redFlags`, `keywordMatches`.
  - `financialSummary`, `timelineSummary`, `actions` — приходят с backend (хранятся в `any`‑подобных полях).
  - `hub?: TenderHubSummary` — **новый хаб‑блок** (см. ниже).
- `PackageAnalysis` — результат пакетного анализа:
  - `packageId`, `summaryScore`, `verdict`, `documents: PackageDocumentAnalysis[]`, `globalIssues`.
  - `hub?: PackageHubSummary` — агрегированный хаб по пакету.
- `CalculatorPreset` — пресет для калькулятора из анализа.


## 4. Хаб тендерного специалиста (Tender Hub)

Цель: дать тендерщику **информацию уровня “хаб”**:
- Red Flags,
- Базовая инфо,
- Спецификации,
- Сроки,
- Платежи,
- Гарантии,
- Требования к участнику,
- Нарушения ФЗ,
- Финансовая оценка,
- Резюме & Действия.

### 4.1. Структуры хаба

- `TenderHubSummary` — краткая сводка по одному документу.
- `PackageHubSummary` — сводка по всему пакету.

### 4.2. Построение хаба на фронтенде

Файл: `frontend/src/utils/hubBuilders.ts`:

- `buildSingleHubFromAnalysis(result: AnalysisResult): TenderHubSummary`
  - Собирает хаб‑данные из уже имеющихся полей `AnalysisResult`.
  - Сейчас часть полей (требования к участнику, точная процедура, заказчик) не заполняется, ждём доработки backend/LLM.

- `buildPackageHubFromAnalysis(pkg: PackageAnalysis): PackageHubSummary`
  - Агрегирует redFlags, НМЦК, ФЗ, глобальные риски по пакету.
  - Используется как задел для будущего UI в `ComplexAudit`.

### 4.3. Компонент TenderHubDashboard

Файл: `frontend/src/components/TenderHubDashboard.tsx`.

- Принимает `result: AnalysisResult` и `hub: TenderHubSummary`.
- Показывает:
  - Верхний блок: **красные флаги** и **индекс безопасности** с вердиктом.
  - Грид карточек: **Базовая инфо / Спецификация / Сроки / Платежи**.
  - Второй ряд: **Гарантии / Финансовая оценка / Резюме и действия (CTA)**.
- CTA-кнопки:
  - "Участвовать";
  - "Запрос разъяснений";
  - "Не участвовать".
- Следующий шаг: добавить логирование нажатий этих кнопок и, возможно, сценарии (черновик решения, выгрузка в отчёт).

### 4.4. Встраивание в Analyzer

Файл: `frontend/src/components/Analyzer.tsx`:

- После получения `analysis` от backend вызывается:
  - `const hub = buildSingleHubFromAnalysis(analysis);`
  - `setResult({ ...analysis, hub });`
- В JSX перед детальными блоками (`Вердикт & SCORE`, `Паспорт`, `DeepAudit`) рендерится `TenderHubDashboard`, если `result.hub` присутствует.


## 5. Основные экраны фронтенда

### 5.1. Analyzer (один документ)

- Загружает PDF/DOC/DOCX/TXT, вызывает `/api/analyze`.
- Показывает:
  - **TenderHubDashboard** (краткий хаб‑вид).
  - Карточку вердикта и индекса безопасности.
  - "Паспорт тендера" (НМЦК, аванс, обеспечение, регион, сроки).
  - `DeepAudit` — детальный чек‑лист с блоками OK/WARNING/CRITICAL.
  - Chat "SINAPS AI" справа.
- Дополнительно:
  - Дисклеймеры по ПДн и юридической ответственности.
  - Логирование ключевых действий через `logEvent` (загрузка файла, запуск анализа, чат).

### 5.2. ComplexAudit (пакет документов)

- Мульти‑upload, вызов `/api/analyze-package`.
- Показывает:
  - Итог по пакету (балл + вердикт).
  - Список документов с оценками.
  - Глобальные риски (`globalIssues`).
  - Детальный блок по выбранному документу (паспорт, риски, красные флаги, финансы, сроки, действия).
  - Панель привязки к базе знаний по клику на `lawReference`.
- Есть кнопка "В калькулятор" и скачивание `.txt`‑отчёта (логируются).
- План: внедрить `PackageHubSummary` и отдельный хаб‑дашборд для пакета (аналог TenderHubDashboard).

### 5.3. DocumentGenerator

- Генерация черновиков:
  - **Протокол разногласий**.
  - **Жалоба в ФАС**.
- Основная логика вынесена в `src/utils/docDrafts.ts`:
  - `buildProtocolDraft(params)`;
  - `buildComplaintDraft(params)`.
- Компонент `DocumentGenerator.tsx` использует эти утилиты и логирует все ключевые действия (открытие инструмента, генерация, копирование, скачивание).

### 5.4. Calculator

- Калькулятор маржинальности с учётом риска (Sinaps Score).
- Может заполняться пресетом из анализа (одиночного или пакетного).
- Показывает финальную прибыль и прибыль с учётом риска.
- Дисклеймер: не является финансовой рекомендацией.

### 5.5. HistoryView

- Показывает историю одиночных и пакетных анализов.
- Использует `/api/history`.
- Содержит дисклеймер, что данные не являются юридически значимыми документами.

### 5.6. KnowledgeView

- База знаний (правовые сниппеты, 44-ФЗ, 223-ФЗ, 135-ФЗ, 152-ФЗ и практика).
- Поисковая строка → `/api/legal/search`.
- Дисклеймер: справочный характер, не заменяет юриста.

### 5.7. Auth

- Авторизация с обязательным принятием:
  - пользовательского соглашения;
  - политики обработки ПДн (152-ФЗ).
- Тексты показаны в модальных окнах на русском.


## 6. Логирование (frontend/src/utils/logger.ts)

- `logEvent(context: string, message: string, level: 'info' | 'warn' | 'error' = 'info', extra?: unknown)`.
- Формат: `[LOG][ISO_TIMESTAMP][CONTEXT][LEVEL] message [extra]`.
- Используется в:
  - Analyzer (загрузка, запуск анализа, чат);
  - ComplexAudit (загрузка пакета, анализ, выбор документа, открытие норм, скачивание отчёта, переход в калькулятор);
  - Calculator (применение пресета, сброс параметров);
  - DocumentGenerator (открытие/закрытие модалок, генерация, копирование, скачивание);
  - HistoryView, KnowledgeView (загрузка истории, поиск по базе).

## 8. Направление развития (roadmap высокого уровня)

1. **Расширить backend-LLM контракт под хаб**:
   - Явно возвращать поля для требований к участнику, процедуры, заказчика, юридических нарушений.
   - Сократить количество post‑обработок на фронте.

2. **Хаб для пакетного анализа**:
   - `PackageHubSummary` + визуальный дашборд на экране ComplexAudit.
   - Отдельный блок "Решение по пакету" + CTA.

3. **Углубление правовой части**:
   - Связка красных флагов с примерами практики ФАС (через KnowledgeView / `/api/legal/search`).
   - Возможность перехода в DocumentGenerator с автозаполнением нарушений.

4. **Профиль / Личный кабинет**:
   - Полные тексты пользовательского соглашения и политики ПДн.
   - Настройки уведомлений, истории, экспортов.

5. **Инфраструктурные меры по ПДн**:
   - Шифрование, разграничение прав, аудит доступа, резервное копирование.
